# BRIEF: Этап 3 — API и настоящий симулятор
Дата: 2026-09-21

## Формулировка своими словами
Симулятор перестаёт писать в SQLite напрямую и вместо этого отправляет показания по HTTP на новый эндпоинт `POST /api/readings` — с ключом API в заголовке и JSON-телом. Сервер проверяет ключ, проверяет, что все три значения — числа и не отрицательные, и только потом пишет через `db.py`. `GET /api/readings?limit=N` отдаёт последние показания в JSON — без проверки ключа, это только чтение уже открытых на сайте данных. Секрет (ключ API) живёт в `.env`, не в репозитории. С этого момента можно запустить симулятор из отдельного терминала/процесса, и данные появятся на сайте так же, как раньше через прямую запись в БД — разница только в способе доставки.

## Критерии успеха
- [ ] `POST /api/readings` с валидным JSON и верным ключом → 201, запись реально появилась в БД
- [ ] `POST /api/readings` без ключа → 401
- [ ] `POST /api/readings` с текстом вместо числа → 400
- [ ] `POST /api/readings` с отрицательным давлением → 400
- [ ] Эти 4 сценария — тесты через `app.test_client()` на временном SQLite-файле (создаётся перед тестом, удаляется после), а не только ручные запросы curl
- [ ] `GET /api/readings?limit=N` отдаёт последние N записей в JSON
- [ ] `simulator.py` не импортирует `db` — только отправляет HTTP-запросы
- [ ] Симулятор запущен в отдельном терминале/процессе, пока сервер уже поднят — новые записи реально появляются на сайте
- [ ] Секрет (`API_KEY`) — в `.env` (gitignored), в репозитории только `.env.example` с плейсхолдером
- [ ] `pytest` зелёный целиком

## Открытые вопросы
Технических развилок, требующих продуктового решения пользователя, не нашёл — ниже стандартные инженерные решения с безопасными допущениями, каждое будет записано в `DECISIONS.md` с причиной:
- Заголовок для ключа: `X-API-Key` (просто, явно, не требует префикса `Bearer`).
- `GET /api/readings` не защищён ключом — это только чтение тех же данных, что уже открыты на `/`, секрета не раскрывает.
- Timestamp генерирует сервер в момент вставки (не клиент) — при запуске с другого компьютера часы могут расходиться, а сервер — источник истины для времени записи.
- Загрузка `.env` — свой минимальный загрузчик на стандартной библиотеке (десяток строк), не `python-dotenv` — задание требует обосновывать новые зависимости, а тут стандартной библиотеки достаточно.
- HTTP-запросы из `simulator.py` — через `urllib.request` (стандартная библиотека), не `requests` — по той же причине.

Если что-то из этого не подходит — скажите до PLAN, поменяю.
