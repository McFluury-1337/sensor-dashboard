## Что сделано
- Локально поставлена MariaDB (Homebrew, `brew install mariadb`) — только для тестов, не для прод-использования; создана тестовая БД `sensor_dashboard_test` и пользователь `sensor_test`.
- `db.py` полностью переписан под два бэкенда: `BACKEND = config.get("DB_BACKEND", "sqlite")`, диалект SQL (плейсхолдер, `CREATE TABLE`, `INSERT IGNORE`/`ON CONFLICT`, upsert) собран в словари `_SQLITE_SQL`/`_MYSQL_SQL`, выбираемые функцией `_sql(key)`, читающей `BACKEND` заново при каждом вызове. Добавлена `_execute(conn, sql, params)` — унифицирует разницу API между `sqlite3.Connection.execute()` (есть) и `pymysql.Connection` (нужен явный `cursor()`).

- `tests/test_db_mysql.py` — 5 тестов, реально подключаются к локальной MariaDB (не мок): создание таблиц и посев порогов, вставка/чтение показаний, обновление порога, upsert пользователя, идемпотентность `init_db()`. Тесты пропускаются (`pytest.mark.skipif`), если MySQL/MariaDB недоступна — не ломают `pytest` там, где её не поднимали.
- `passenger_wsgi.py` — `from app import app as application`, проверено импортом (`callable(passenger_wsgi.application) == True`).
- `harness/PROJECT.md`, `DECISIONS.md` обновлены.

## Отклонения от плана
Одно техническое, найденное и исправленное в процессе: изначальный вариант ветвления SQL (`if BACKEND == "mysql": PLACEHOLDER = ...` на уровне модуля) вычислялся один раз при импорте — та же ошибка, что чинили с `DB_PATH` на Этапе 3: `monkeypatch.setattr(db, "BACKEND", "mysql")` в тестах не имел бы эффекта, потому что `PLACEHOLDER`/`CREATE_READINGS` и т.д. уже были бы зафиксированы под тот бэкенд, что стоял в `.env` при запуске тестов. Переделано на функцию `_sql(key)`, читающую `BACKEND` заново при каждом вызове — так же, как раньше `path=None` вместо `path=DB_PATH`.
