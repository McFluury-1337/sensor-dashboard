## Шаги

1. Поставить MariaDB локально через Homebrew (`brew install mariadb`), поднять только для тестов, создать тестовую БД/пользователя — не трогает продакшен, не попадает в репозиторий.
2. Отрефакторить `db.py`: добавить `BACKEND = config.get("DB_BACKEND", "sqlite")`, ветвление `get_connection()` (sqlite3 vs `pymysql.connect`), вспомогательную `_execute(conn, sql, params)` — унифицирует разницу API (`sqlite3.Connection.execute()` — есть, у `pymysql.Connection` — нет, нужен явный `cursor()`). Разные CREATE TABLE (автоинкремент, типы, длины ключей) и разные конструкции upsert (`INSERT OR IGNORE`/`ON CONFLICT` в SQLite vs `INSERT IGNORE`/`ON DUPLICATE KEY UPDATE` в MySQL) — отдельными константами по бэкенду; обычные SELECT/INSERT/UPDATE — общим текстом с плейсхолдером (`?` или `%s`) через одну переменную.
3. Добавить в `config`/`.env.example` переменные: `DB_BACKEND`, `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`.
4. Добавить `pymysql` в `requirements.txt`, записать решение в `DECISIONS.md` (обоснование выбора и отказ от `mysqlclient`).
5. Написать `tests/test_db_mysql.py` — реальный интеграционный тест против локальной MariaDB (создание таблиц, insert/select/update, сид порогов и пользователя, upsert). Тест пропускается (`pytest.skip`), если локальной MySQL/MariaDB нет — чтобы не ломать `pytest` там, где её не поднимали (например, в CI без базы).
6. Прогнать весь `pytest` — старые 31 тест на SQLite не сломаны, новые тесты на MySQL зелёные при поднятой MariaDB.
7. Написать `passenger_wsgi.py` (`from app import app as application`) — стандартный вход для Phusion Passenger.
8. Обновить `harness/PROJECT.md` (новый бэкенд, `passenger_wsgi.py`, переменные окружения), написать `harness/stage-6/REPORT.md` по части A, закоммитить и запушить.
9. Отдельным сообщением — пошаговый ранбук по Части B (хостинг на Beget), без коммита в репозиторий (это инструкция для вас, не код проекта, но могу оформить как `harness/stage-6/RUNBOOK.md`, если удобнее иметь под рукой в репозитории — как решите).

## Альтернативы

- SQLAlchemy (или другой ORM) вместо ручного ветвления SQL: отвергнуто — задание с самого начала держит стек тонким («Flask и SQLite хватает», без ORM), а `db.py` и так уже единственная точка доступа к БД; ORM решил бы проблему синтаксиса ценой новой зависимости и нового способа думать о запросах ради экономии полутора десятков строк веток.
- `mysqlclient` вместо `PyMySQL`: отвергнуто — требует компилятора и `libmysqlclient-dev` при установке, на shared-хостинге (как у Beget) это часто недоступно или требует лишней возни; `PyMySQL` — чистый Python, ставится `pip install --user` без сборки.
- Определять бэкенд по наличию `pymysql` в окружении (auto-detect), а не по явной переменной `DB_BACKEND`: отвергнуто — неявное поведение («тихо переключились на MySQL, потому что кто-то поставил пакет») сложнее отлаживать, чем явный флаг в `.env`.
