1. Если что-то не сходится с текстом — правлю README, а не подгоняю окружение под текст задним числом.

5. Написать `harness/stage-7/REPORT.md`: что сделано, что подтверждено дословной проверкой README, что осталось за рамками (хостинг), явный список несделанного по критериям задания «Что я смотрю на сдаче».
6. Закоммитить и запушить.

## Альтернативы

- Оставить инструкции только в `harness/PROJECT.md`, а в README — ссылку на него: отвергнуто — куратор явно просит инструкцию именно в README («я разворачиваю проект у себя по твоему README»), заставлять его читать `harness/` в поисках команд — плохой UX для ровно того сценария, который он описал как критерий.
- Инлайнить весь ранбук по Beget прямо в README вместо ссылки на `harness/stage-6/RUNBOOK.md`: отвергнуто — README тогда раздувается на две разные аудитории (запустить у себя за 5 минут vs развернуть на конкретном хостинге за вечер); короткая версия в README + ссылка на подробный ранбук короче для читателя и не дублирует один и тот же текст в двух местах.
- Считать этап «сданным» без хостинга, раз код готов: отвергнуто — задание прямо перечисляет «ссылка работает, данные живые» и «сайт живёт минимум неделю» как критерии; закрывать этап отчётом без честной оговорки было бы искажением состояния работы.

## Риски

- 🟡 Дословная проверка README (шаг 2) может найти реальные несостыковки (забытая команда, неверный путь) — если найдёт, это находка, а не повод пропустить шаг.
- 🟢 Само README — не код, изменения не затрагивают логику/тесты.
