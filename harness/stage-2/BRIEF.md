# BRIEF: Этап 2 — состояние и графики
Дата: 2026-09-21

## Формулировка своими словами
Сайт должен сам определять состояние системы (норма/предупреждение/неисправность) по показанию датчиков, используя пороги, хранящиеся в БД, а не зашитые в коде. На главной странице появляются: текстовый+цветной индикатор текущего состояния, график Chart.js по последним 50 показаниям с переключателем сырые/нормализованные/стандартизированные, и таблица «среднее ± σ» по трём состояниям, посчитанная живьём из `readings`. С этого этапа логика (определение состояния, нормализация, стандартизация) пишется по TDD: сначала тест с конкретными числами, потом код, пока тест не позеленеет — и эти функции не трогают ни БД, ни Flask, только вход → выход.

## Контекст
- Этап 1 сдан и запушен (`db.py`, `simulator.py`, `app.py`, `requirements.txt`), критерий подтверждён (см. `harness/stage-1/REPORT.md`).
- Таблица `readings` уже существует и наполняется симулятором.
- Есть реальные данные из НИР для сверки: `data_raw.csv` (300 записей, по 100 на состояние, колонки temperature/pressure/vibration/state) и текст `НИР_Зеленин_v5.docx` с Таблицей 1 (раздел 3.2): норма 69.69±2.72 / 5.01±0.29 / 0.51±0.11, предупреждение 78.43±3.54 / 5.78±0.43 / 0.88±0.14, неисправность 88.12±5.34 / 6.70±0.49 / 1.56±0.23 (температура/давление/вибрация).
- Три инженерных решения приняты и записаны в `DECISIONS.md`: пороги (середина между соседними средними из Таблицы 1, округлённо — temp 74/83, pressure 5.4/6.2, vibration 0.7/1.2), правило агрегации состояния («худшее из трёх»), окно графика (последние 50 записей).
