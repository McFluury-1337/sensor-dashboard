# Карта проекта: sensor-dashboard

## Что это
Пет-проект: веб-дашборд на Flask, показывающий показания датчиков (температура, давление, вибрация), которые генерирует локальный симулятор на основе генератора из НИР автора. Сайт сам определяет состояние системы по порогам и живьём считает статистику по состояниям. Делается для практики полного цикла веб-разработки — от БД до хостинга.

## Стек
- Python 3.14 (venv в `.venv/`, в репозитории не хранится)
- Flask 3.1.3 — веб-сервер, одна страница без шаблонов и стилей
- SQLite (файл `sensors.db`, в репозитории не хранится) — хранилище показаний и порогов, доступ только через `db.py`, чтобы позже можно было переключиться на MySQL
- Chart.js 4 через CDN (`<script>` в `app.py`) — график показаний с переключателем сырые/нормализованные/стандартизированные
- pytest — тесты чистых функций (`state.py`, `preprocessing.py`) и сверка с данными НИР, зависимость только для разработки (`requirements-dev.txt`)

## Структура
```
app.py               # Flask-приложение: индикатор состояния, график Chart.js, таблица среднее±σ, таблица последних 50 записей
db.py                # единственный модуль работы с БД (readings + thresholds) — точка переезда на MySQL
state.py             # чистые функции определения состояния по порогам (без БД и Flask)
preprocessing.py     # чистые функции normalize()/standardize() (без БД и Flask)
simulator.py         # генерирует одну запись показаний (норма/предупреждение/неисправность) и пишет через db.py
requirements.txt     # рантайм-зависимости (flask)
requirements-dev.txt # зависимости для разработки (pytest)
pytest.ini           # добавляет корень проекта в PYTHONPATH для tests/
tests/               # pytest: test_state.py, test_preprocessing.py, test_against_nir.py + fixtures/data_raw.csv (300 записей из НИР)
harness/             # PROJECT.md и BRIEF/PLAN/REPORT по этапам (harness/stage-N/)
```

## Ключевые модули и точки входа
| Модуль | Где | За что отвечает |
|--------|-----|-----------------|
| `db.py` | `db.py` | Подключение к SQLite, таблицы `readings` и `thresholds`, CRUD-функции. Единственное место с SQL. Все функции принимают `path=DB_PATH` — для тестов подставляется временный файл. |
| `state.py` | `state.py` | `classify_metric(value, warn, fault)` — состояние одного параметра по порогам; `classify_reading(temp, pressure, vibration, thresholds)` — итоговое состояние показания, правило «худшее из трёх» (см. DECISIONS.md). Чистые функции, без БД/Flask. |
| `preprocessing.py` | `preprocessing.py` | `normalize(values)` — приведение к [0,1]; `standardize(values)` — z-score. Чистые функции, без БД/Flask. |
| `simulator.py` | `simulator.py` | Выбирает состояние, генерирует temp/pressure/vibration через `random.normalvariate` по mu/sd из НИР, пишет одну запись за запуск через `db.py`. |
| `app.py` | `app.py` | Flask-роут `/` — индикатор состояния (слово+цвет) по последнему показанию, график Chart.js по последним 50 записям с переключателем видов данных, таблица среднее±σ по трём состояниям (по всей истории), таблица последних 50 записей. |

## Как запустить / проверить
```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt -r requirements-dev.txt
python simulator.py      # добавить одну запись в sensors.db (можно запускать многократно)
python app.py             # запустить сайт на http://127.0.0.1:5000/
pytest                     # прогнать все тесты (логика состояний, предобработки, сверка с НИР)
```

## Known issues
- `app.py` собирает HTML прямой f-строкой без экранирования — безопасно только пока в таблице нет строковых данных, приходящих извне (сейчас всё из своего симулятора).
- `app.run(debug=True)` — только для разработки, для деплоя нужно будет заменить на прод-WSGI сервер.
- `simulator.py` пишет ровно одну запись за запуск, непрерывного сбора (цикл/планировщик) пока нет — отдельный этап.
- Таблица «среднее ± σ» на сайте группирует показания по вычисленному через пороги состоянию (другого способа для реальных данных нет), поэтому её числа заметно отличаются от Таблицы 1 НИР (которая считалась по истинным меткам генерации) — см. `LESSONS.md`, запись про «худшее из трёх». Это ожидаемое поведение, не баг.
- На macOS порт 5000 может быть занят AirPlay Receiver — см. `LESSONS.md`.
- Порог/агрегация/окно графика — первые три инженерных решения проекта, записаны в `DECISIONS.md` с обоснованием.
