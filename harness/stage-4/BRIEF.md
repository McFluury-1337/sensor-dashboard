# BRIEF: Этап 4 — админка
Дата: 2026-09-21

## Формулировка своими словами
Появляется `/login` (форма логин+пароль) и `/admin` (доступен только после входа — иначе редирект на `/login`). Пароль хранится в БД только как хеш (`werkzeug.security`), никогда открытым текстом. Под логином — две формы: ввести показание вручную (та же валидация, что и у API — числа, не отрицательные) и поправить пороги состояний (те самые, что определяют норма/предупреждение/неисправность с Этапа 2). Изменения сразу видны на главной странице — отдельного шага «применить» не нужно, потому что состояние и так всегда считается заново при каждом открытии `/`.

## Контекст
- Этап 3 сдан: API с ключом, симулятор через HTTP, `db.py` уже тестируемый (`path=None` + monkeypatch), `.env`/`config.py` уже есть (там же будет жить пароль администратора и секрет сессии).
- Пороги хранятся в таблице `thresholds` (Этап 2), читаются функцией `db.get_thresholds()` — обновлять их нужно новой функцией `db.update_threshold(...)`, самого поля для записи пока нет.
- Валидация «число, не отрицательное» для показаний уже есть в `app.py` (`_parse_reading_payload`, сейчас работает только с JSON-телом API) — для формы админки её нужно переиспользовать, а не дублировать.

## Критерии успеха
- [ ] `/admin` без логина → редирект на `/login`
- [ ] Вход с неверным паролем не пускает (остаёшься на `/login`, доступа к `/admin` нет)
- [ ] Вход с верным логином/паролем → доступ к `/admin`
- [ ] Форма «ввести показание вручную» на `/admin` пишет в `readings` через ту же валидацию, что и API
- [ ] Форма «поправить пороги» на `/admin` пишет в `thresholds`, изменение сразу видно на `/` (индикатор состояния/таблица среднее±σ используют новые пороги)
- [ ] В `sensors.db` пароль администратора хранится хешем (не открытым текстом) — проверяется вручную через sqlite3
- [ ] Минимум 2 теста через `app.test_client()`: без логина редирект, с неверным паролем вход не пускает — по факту будет больше
- [ ] `pytest` зелёный целиком

## Открытые вопросы
Продуктовых развилок нет, все решения — стандартные инженерные допущения, будут в `DECISIONS.md`:
- Логин по паре логин+пароль (не только пароль) — таблица `users(username, password_hash)`, привычнее и проще тестировать (можно отдельно проверить «неверный пароль» и «неверный логин»).
- Учётные данные администратора по умолчанию — сгенерирую случайный пароль в `.env` (как раньше `API_KEY`), заведу через `ADMIN_USERNAME`/`ADMIN_PASSWORD`, `db.init_db()` сам засеет хеш при первом запуске, если пользователей ещё нет.
- Секрет сессии Flask (`SECRET_KEY`) — тоже в `.env`, генерирую случайно.
- Обратная связь по формам («показание добавлено», «неверные пороги») — через `flash()` (встроено в Flask, новых зависимостей не требует).
- Пороги валидируются: оба числа, нижняя граница меньше верхней, обе неотрицательные — иначе форма не сохраняет и показывает ошибку.

Если что-то не подходит — скажите до PLAN.
