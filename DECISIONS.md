## 2026-09-22 — Внешний вид: Pico CSS classless, тёмная приборная тема, числа моно
- Решение: подключили `pico.fluid.classless.min.css` через CDN (один `<link>`), разметку перевели на семантические теги (`header`/`nav`/`main`/`footer`/`section`/`table`/`form`/`fieldset`), тема — тёмная (`data-theme="dark"`) с одним переопределённым акцентом `--pico-primary: #2fb0c7`; числа в таблицах — моноширинный системный шрифт (`ui-monospace` и фоллбэки), обычный текст — шрифт Pico по умолчанию. Перед вёрсткой поставили официальный плагин `frontend-design` (`claude-plugins-official`) и оттолкнулись от его дизайн-плана: подобрали палитру и типографику под предметную область (приборная панель промышленного мониторинга), а не под шаблон дашборда.
- Почему: задание явно требует classless-Pico и запрещает Bootstrap/Tailwind; приборная эстетика (тёмный фон, один акцент только для состояния, моно-цифры) — осознанный выбор под предмет (датчики/пороги/аварийные состояния), а не дефолтный «SaaS-дашборд» (тёплый бежевый + засечка или тёмный + неон), которого явно избегает `frontend-design`.
- Затронуто: `app.py` (`PAGE_STYLES`, `_page()`, `_nav_html()`, разметка `/`, `/login`, `/admin`).

## 2026-09-22 — Таблицы: одна колонка по умолчанию, две — от 900px, скролл — как запасной вариант
- Решение: сетка из двух таблиц (`.tables-grid`) — одна колонка по умолчанию, две колонки только от `900px`; `auto-fit`/`minmax` не использовали. Внутри каждой таблицы — обёртка `overflow-x: auto` на случай, если контент всё равно не поместится.
- Почему: `grid-template-columns: repeat(auto-fit, minmax(460px, 1fr))` на первый взгляд решает задачу «две колонки на широком, одна — на узком», но минимальный размер трека (460px) — это жёсткий пол, который ломает страницу уже при 390px (грid не даёт треку сжаться меньше минимума, даже если сами ячейки готовы сжаться через `min-width: 0`). Явный медиа-запрос с фиксированным брейкпоинтом предсказуем и не зависит от этой особенности grid.
- Затронуто: `app.py` (`PAGE_STYLES`, разметка `/` и `/admin`).

## 2026-09-21 — Админка: логин+пароль, сессия Flask, посев админа из .env
- Решение: таблица `users(username, password_hash)`; `/login` принимает логин и пароль (не только пароль); сессия — стандартный `Flask session` с `SECRET_KEY` из `.env`; при первом `init_db()`, если пользователей ещё нет, сеется один админ из `ADMIN_USERNAME`/`ADMIN_PASSWORD` (если пароль не задан — посев пропускается, дефолтного пароля в коде нет).
- Почему: логин+пароль (а не только пароль) — обычная практика и позволяет отдельно протестировать «неверный логин» и «неверный пароль»; `Flask session` подписывает cookie секретом — самодельная проверка через простую куку подделывается в браузере вручную, это и есть механизм «сессии» из задания. Хранить дефолтный пароль в коде — плохая практика (checked-in credential); генерация в `.env` (как раньше `API_KEY`) избегает этого и держит секрет вне репозитория.
- Затронуто: `db.py` (таблица `users`, `get_user`, `upsert_user`), `app.py` (`login_required`, `/login`, `/admin/logout`), `.env`/`.env.example`.

## 2026-09-21 — Форма ручного ввода переиспользует валидацию API
- Решение: `POST /admin/readings` использует ту же функцию `_parse_reading_payload`, что и `POST /api/readings` — просто передаёт `request.form` вместо JSON-словаря.
- Почему: правило «число, не отрицательное» одно и то же для показания независимо от источника (API или форма админки); дублировать его — плодить два места, которые могут разойтись при следующей правке. Понадобилась одна правка в `_parse_reading_payload` (убрать `isinstance(payload, dict)` — `request.form` не `dict`, а `ImmutableMultiDict`), после чего функция одинаково работает с обоими источниками.
- Затронуто: `app.py` (`_parse_reading_payload`, `admin_create_reading`).

## 2026-09-21 — Своя загрузка .env вместо python-dotenv, urllib вместо requests
- Решение: `.env` читается собственным загрузчиком в `config.py` (10 строк на стандартной библиотеке), а `simulator.py` отправляет HTTP-запросы через `urllib.request`, а не через `requests`.
- Почему: задание требует обосновывать каждую новую библиотеку; для одного файла `.env` и одного JSON POST стандартной библиотеки достаточно — добавлять `python-dotenv` и `requests` было бы зависимостями «на вырост» без функциональной необходимости.
- Затронуто: `config.py` (новый), `simulator.py`.

## 2026-09-21 — GET /api/readings не защищён ключом API
- Решение: `POST /api/readings` проверяет ключ (`X-API-Key`), `GET /api/readings` — нет.
- Почему: GET только читает те же данные, что уже открыты без всякой авторизации на странице `/`; добавлять защиту чтения не от чего — секрета там нет, а лишняя проверка усложнила бы код без выигрыша в безопасности.
- Затронуто: `app.py`.

## 2026-09-21 — Timestamp показания генерирует сервер, не клиент
- Решение: `POST /api/readings` игнорирует любой timestamp от клиента (в теле запроса его и не ожидается) — сервер сам ставит `datetime.now().isoformat()` в момент вставки.
- Почему: по условию этапа симулятор может запускаться с другого компьютера — его часы могут расходиться с сервером; сервер как единственный источник истины для времени записи проще и надёжнее, чем сверка/коррекция чужих часов.
- Затронуто: `app.py` (`create_reading`).

## 2026-09-21 — Окно графика: последние 50 показаний
- Решение: график Chart.js и таблица на главной странице показывают последние 50 записей из `readings`.
- Почему: то же число уже используется в таблице Этапа 1 (`db.get_latest_readings(50)`) — единообразно, не плодит вторую константу без причины.
- Затронуто: `app.py`, `db.py` (переиспользуем существующую функцию).

## 2026-09-21 — Итоговое состояние показания: «худшее из трёх»
- Решение: если по одному показанию температура/давление/вибрация попадают в разные категории (норма/предупреждение/неисправность), итоговым состоянием считается самая серьёзная из трёх категорий.
- Почему: при независимой генерации шума по каждому параметру (см. `simulator.py`) параметры иногда расходятся по категориям; для мониторинга безопаснее не занижать состояние — консервативный выбор «худшее из трёх», а не голосование или взгляд только на температуру.
- Затронуто: новый модуль логики состояний (Этап 2).

## 2026-09-21 — Пороги состояний по датчикам
- Решение: границы между состояниями — середина между соседними средними из Таблицы 1 (раздел 3.2 НИР), округлённая: температура 74 / 83, давление 5.4 / 6.2, вибрация 0.7 / 1.2. Ниже нижней границы — «норма», между границами — «предупреждение», выше верхней — «неисправность».
- Почему: реальная Таблица 1 из `НИР_Зеленин_v5.docx` даёт норма 69.69±2.72 / предупреждение 78.43±3.54 / неисправность 88.12±5.34 (температура, аналогично для давления и вибрации). Середина между соседними средними для температуры даёт 74.06 и 83.27 — совпадает с примером куратора («норма примерно до 74, предупреждение до 83»), значит метод рабочий; тот же метод применён к давлению и вибрации. Проверено на `data_raw.csv` (300 записей, по 100 на состояние) — метод устойчив, хотя границы состояний по сырым данным слегка перекрываются (это ожидаемо: сам НИР показывает, что состояния различимы в среднем, а не по жёсткой границе одного показания).
- Затронуто: таблица `thresholds`, модуль определения состояния (Этап 2).
